# VERIFYING — reproducing and checking this repository

Everything here is meant to be checkable by a third party with no access to the
project's history. Commands are given verbatim; where a check cannot be
performed from the repository alone, that is stated rather than papered over.

`METHOD.md` explains *why* these checks exist. This file is *how*.

---

## 1. Prerequisites

| tool | version | why |
|---|---|---|
| Lean 4 / `elan` | **`leanprover/lean4:v4.33.0-rc2`** (the content of `lean-toolchain`) | the kernel that checks the proofs |
| `lake` | ships with the toolchain, must be **on `PATH`** | build, and required by `tools/proportion.go` |
| Go | any recent toolchain (`go run` only; no modules, no dependencies) | the ledger tool |
| Python 3 | stdlib only | the two `forensics/` guards |
| `git`, `curl` | — | fetching dependencies |

`elan` reads `lean-toolchain` automatically, so simply having `elan` installed
is enough; it will fetch `v4.33.0-rc2` on first use.

### Dependencies

`lakefile.toml` requires one direct dependency:

```toml
[[require]]
name = "zeta23"
git = "https://github.com/anthropics/zeta-23-lean"
rev = "main"
```

Mathlib and everything else is inherited transitively from it. **`lakefile.toml`
says `main`, but `lake-manifest.json` pins the exact revisions** — that file is
tracked precisely so a third party gets the same build:

* `zeta23` → `3635e74826a4c1fcece7d1cd2b6fa75e43a00510`
* `mathlib` → `51e6992efd06126df61a496bebf8f49482a4e129`
* plus pinned revs for `batteries`, `aesop`, `Qq`, `proofwidgets`,
  `importGraph`, `LeanSearchClient`, `plausible`, `Cli`.

`https://github.com/anthropics/zeta-23-lean` was reachable (HTTP 200,
unauthenticated) at the time this file was written. If it ever becomes
unavailable the Lean build cannot be reproduced from this repository alone —
there is no vendored copy here.

Use `lake` (not `lake update`) so the manifest pins are honoured:

```bash
lake exe cache get     # Mathlib oleans, if the cache is available for this rev
lake build             # slow on a cold cache: ~3700 build jobs
```

`.lake/` is gitignored (it is ~9 GB locally) and is regenerated by the build.

## 2. The ledger tool

```bash
go run tools/proportion.go             # print the line, do not write
go run tools/proportion.go -append     # print it and append to PROPORTION.log
```

It must be run **from the repository root** (it uses the working directory as
the root) and **after a successful `lake build`**.

It shells out to `lake env lean …` three times, so **`lake` must be on `PATH`**.
If it is not, the very first guard — the declaration audit — fails to launch and
the tool reports the escalation with empty command output and exits `4`:

```
ESCALATION: audit/Declarations.lean failed — a claimed name does not exist.

```

i.e. an *empty* exit-4 escalation is the signature of a missing `lake`, not of a
missing declaration. A genuine declaration failure prints Lean's error text.

### Exit codes

| code | meaning |
|---|---|
| `0` | line printed (and appended, with `-append`) |
| `1` | I/O or parse failure (`tools/metric.json` unreadable/invalid, axiom audit errored) |
| `3` | **base-hash drift**: the normalised axiom statements in `Riemann/Assumptions.lean` hash to something other than `base.hash` in `tools/metric.json`, and `base.version` was not bumped. The log line is **not** written |
| `4` | **declaration audit failed**: `lake env lean audit/Declarations.lean` did not compile — a name the registers make claims about does not exist (or `lake` is missing; see above) |
| `5` | **a regression file COMPILED**: some `audit/regression/*.lean` succeeded. That file is supposed to fail; success means the trusted base is inconsistent again (ISSUES #8) |

Note that codes `4` and `5` are checked *before* anything is computed, and code
`3` aborts before the log line is appended. The tool is a gate, not a reporter.

## 3. Checking the claims

### 3.1 The trusted base is exactly `Riemann/Assumptions.lean`

The audit is

```bash
grep '^axiom' Riemann/Assumptions.lean
grep -rn '^axiom' Riemann/ audit/          # nothing outside Assumptions.lean
```

**Caveat, stated because it matters for anyone repeating the count:** the first
grep currently returns **10** lines, not 9. One of them —

```
Riemann/Assumptions.lean:26:axiom must extend it**:
```

— is prose inside a doc comment that happens to begin a line with the word
`axiom`. The **nine real axioms** are:

```
zetaNonempty              xiPrimeFamily              closePairsZeta
fujii_ineffective         fujii_closePair_bookkeeping
zeta23_xiPrime            levinson_montgomery
baseline_przz             baseline_zeta23
```

`tools/proportion.go` is not fooled by this: `baseHash` and `countSources`
strip block comments and line comments before matching, so the tool's own count
(printed as `axioms declared in Riemann/: N (…)`) is the real one. If you want a
grep that agrees, strip comments first, or read the tool's output.

The second grep confirms the base does not leak: the only other matches in
`Riemann/` are the words "axiom." occurring mid-sentence in `Gaps.lean` and
`Blindness.lean` docstrings. There are no `axiom` declarations in `audit/`.

### 3.2 `axioms: 2` in the ledger vs 9 in the base — not a contradiction

The ledger line ends with `axioms: 2 (Riemann.baseline_zeta23,
Riemann.zetaNonempty)`. That field is **not** the size of the trusted base. It
is the non-standard axiom set in the **cone of the best-scoring certified row**
(here `Riemann.certified_std`), as reported by `#print axioms` — i.e. *which* of
the nine assumptions the current headline number actually leans on. The other
seven are declared but not consumed by that row.

* **9** = what the project is allowed to assume (`Assumptions.lean`).
* **2** = what the 67.25% figure actually uses.

Both numbers are worth reading; they answer different questions.

### 3.5 The regression files must FAIL to compile

```bash
lake env lean audit/regression/Boom_2026-08-13.lean ; echo "rc=$?"
```

**The pass condition is a non-zero `rc`.** `Boom_2026-08-13.lean` derives
`False` from an earlier version of the axioms (via `farmer_ki` instantiated at a
trivial `closePairs`); it must never compile again. `tools/proportion.go` runs
every file in `audit/regression/` and exits `5` if any of them succeeds.

### 3.6 The declaration audit

```bash

```

Must be `0`. It `#check`s every name the registers make claims about, so it
fails the moment a claimed name disappears or is renamed. `LOOP.md` records that
it was verified end-to-end by appending a fictional name and watching the
escalation fire.

`Assumptions.lean`). `tools/proportion.go` strips block and line comments before

## 4. The forensics guards

Both are stdlib-only Python 3 and self-test when run directly.

```bash
python3 forensics/lemma1_guard.py       # prints a self-test over constant models
python3 forensics/provenance_lint.py    # prints the provenance report
```

* **`lemma1_guard.py`** checks a candidate form-factor model `D` on `[1, λ]`
  against Goldston's Lemma 1 — under RH, `∫_B^{B+1} F ≤ 3` uniformly for all
  `B ≥ 1`. Its self-test walks constant models `D = 1, 2, 3, 4`; the `4` case
  must report `VIOLATES RH (Lemma 1)`. Applied retroactively it killed every
  `c ≥ 4` row the project had published.
* **`provenance_lint.py`** builds the dependency DAG of the project's numerical
  inputs (`explicit_formula`, `RH`, `positivity`, `F_on_[0,1]`, `EP1`,
  `class_closure`, `Lemma1_cap3`, `CMR_1.3208`, `GGOS_floor`, `sieve_twin`,
  `MRT_corr`, `GM_bridge`) and flags **CIRCULAR** / **SCALE** / **QUALITY**. It
  also propagates an RH-conditional flag, which is what produced the mechanical
  `T3(b)` verdicts in `FAILURES.md`.

Neither is wired into `proportion.go`; they are run by hand *before* a table is
built, per the operational rules in `LOOP.md`.

## 6. Sealed blind reads

The convention, used throughout `forensics/`:

```bash
sha256sum <file> | cut -c1-16
```

The first 16 hex characters are quoted in the register entry that announces the
sealed file, **before** the comparison it will be scored against is run.

Three seals are documented in the registers, and **all three verify** against
the files as committed:

| seal | file | registered in |
|---|---|---|
| `5d385586e174ddc4` | `forensics/T3b_predictions_VPS.md` | `FAILURES.md` §T3(b), `SESSION.md` |
| `460ccd415bc031e1` | `forensics/blind_trichotomy_v2.md` | `FAILURES.md` §T2b, `SESSION.md` |
| `246745bcc293b648` | `forensics/W28_atom_interface_cold.md` | `LEADS.md`, `SESSION.md` |

Check them with:

```bash
for f in forensics/T3b_predictions_VPS.md \
         forensics/blind_trichotomy_v2.md \
         forensics/W28_atom_interface_cold.md; do
  printf '%s  %s\n' "$(sha256sum "$f" | cut -c1-16)" "$f"
done
```

The other files in `forensics/` (`tri_read_comparison.md`, `fractures.tsv`,
`restatements.tsv`, the two `.py` guards) carry **no** registered seal — they are
analysis and instruments, not sealed predictions. Do not read the sealing
convention as covering the whole directory.

**A seal proves the file was fixed before the comparison; it does not prove the
blind was clean.** `FAILURES.md` §T2b records that this exact distinction bit:
the sealed file's *wording* overstated how blind the read had been, the file was
not edited to fix it, and the register says plainly that "the hash outranks the
wording". Three exposure channels are named there. Read that section before
citing any of these seals as evidence.
